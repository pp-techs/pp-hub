# M24 — The REST/WOPI write collision

✅ done · part of the [delivery milestones index](../milestones.md).

- The only P0 item that lost data during ordinary use: `file_locks` existed and
  only the WOPI endpoints honoured it, so while one person had a document open,
  another's `PUT /nodes/{id}/versions` was accepted against no lock and the next
  save silently discarded one side.
- **Decision taken: refuse, do not take a lock.** A REST upload has no lock
  lifecycle — no unlock, no `REFRESH_LOCK` — so a lock taken there would only be
  released by the sweep, which is worse than an editor left open over lunch
  blocking a colleague.
- `Server.lockedByEditor` is called from `handleUploadVersion` **before**
  `parseUpload`, so a locked file is refused before a multi-gigabyte body is
  read, and from `handleRestoreVersion`, which repoints `current_version_id` just
  as directly. Trash/move/rename are out of scope: they do not change bytes.
- Since M30 the replacement path is a tus upload, checked at creation and again
  at commit, answering **423 Locked** there because tus reserves 409 for an offset
  mismatch; restore-version still answers 409.
  `TestReplacementUploadHonoursTheEditorLock` replaced the REST-upload test.
