# M49 — Guest access

✅ done · part of the [delivery milestones index](../milestones.md). The design
in force is [guest-access.md](../guest-access.md).

- **The decision.** Somebody with no account opens what was shared with their
  address by proving the address with a one-time code. The identity is a
  `users` row of `kind = 'guest'` (no OIDC identity, `oidc_iss = ''`), so
  grants, comments and notifications need no second kind of principal, and the
  access is M42's external direct grant at view level, so the resolver is
  unchanged. Comments already take `CapView`, so "view + comment" needed no new
  capability.
- **Switch.** `guest_access` (`system_config`, off), in Admin › Settings ›
  Sharing. Guests count only while it and `external_sharing_enabled` hold;
  either off 403s every guest request at once.
- **Proof.** `GET /auth/guest`, `POST /auth/guest/code`,
  `POST /auth/guest/verify` (`internal/guest`, `httpapi/guest.go`). A code goes
  only to an address with a live view invitation or a guest holding a grant,
  never to one a real account uses; the answer is `204` either way. Six
  digits, ten minutes, five tries, three mails an hour per address
  (`guest_otps`), and a per-IP limit in front. A wrong code is `422`, because
  the web client takes `401` to mean the session is gone.
- **Confinement.** The `authenticated` middleware lets a guest session through
  an allowlist of read-and-comment routes (`guestRoutes`) and answers 403 to
  the rest; `GET /spaces/` answers `[]` for a guest. `Provision` never gives a
  guest a personal space; `ListUsers`, `CountUsers` and `AdminStats` count
  members only.
- **Sharing.** A guest is found by `GetUserByEmailNorm` like any verified
  account; an edit share to one is 422. Verification adopts only the **view**
  invitations for the address (`TakePendingShares … view_only`); an edit
  invitation waits for the address's own sign-in. Invitation mail says "enter
  this address and we send a code" instead of "create an account" when guests
  are on.
- **Promotion.** A verified Logto sign-in (`resolveUser`) or org sync
  (`resolveMember`) with the same address, in any letter case, re-points the
  guest row (`AdoptUserIdentity` now also sets `kind = 'member'`), keeping its
  id, grants and comments.
- **Web.** A code form under SSO on the sign-in page; a reduced shell for a
  guest (brand, "Shared from outside", sign-out; no space switcher, storage,
  search, settings or versions); a "Guest" badge in the share list.
- **Migration** `0029_guest_access.sql`.
- **Tests.** `httpapi/guest_db_test.go` (end to end through the router, the
  route walk, the allowlist matcher, code single-use, burn and expiry, view-only
  adoption, switches, promotion), `notify/messages_test.go`.
- **Not in it:** edit or re-share for a guest, notification mail to a guest,
  purging guest rows, revoking a guest's sessions when their last grant goes
  (a session with no grant reaches nothing), guests on share links, kanban
  boards.
