# M30 — Resumable upload and honest accounting

✅ done · part of the [delivery milestones index](../milestones.md).

- What made it urgent was an incident: behind a 60s proxy `readTimeout` and
  Cloudflare's 100 MB body cap, a multipart POST failed for any file whose upload
  took over a minute. The durable answer is requests that stay short however big
  the file is.
- **Decision: tus 1.0.0, and no multipart path beside it.** The protocol already
  specifies where an upload stands (HEAD), what a mismatched offset answers (409
  with the server's offset) and how an abandoned one is let go (DELETE), and a
  second route for file content would be a second place to enforce the cap, the
  quota and the editor lock. `POST /spaces/{spaceID}/files` and
  `POST /nodes/{nodeID}/versions` are **gone**; version list and restore stay.
  Only the core protocol plus creation and termination extensions are
  implemented, and `Upload-Defer-Length` is refused on purpose.
- `POST /api/v1/uploads` takes `Upload-Length` and metadata (`filename`,
  `space_id`, `parent_id` for a new file; `node_id` alone to replace one). The
  declared length is checked against the cap and the space quota **plus bytes
  other in-flight uploads have promised** (`PendingUploadBytes`), so ten parallel
  uploads cannot each pass a check the ten together would fail; both answer 413
  before a byte is accepted. A replacement is refused with **423** while an
  editor lock is live. The creation POST may carry the first chunk, so small
  files cost one request, and `Location` is set before a byte is read.
- `HEAD` reports the offset, `PATCH` appends, `DELETE` abandons; an upload is
  visible only to its creator (404 otherwise). An interrupted PATCH keeps what
  arrived: the append runs on a detached context, copies through a `LimitReader`
  bounded by the declared length and fsyncs the staging file before the row's
  offset advances, so a crash can lose the chunk's tail but never leave the row
  ahead of the file. A staging file shorter than the recorded offset is discarded
  rather than resumed, because resuming would splice zeros in.
- The final PATCH **commits before it answers**, re-checking authorization and
  the lock; a lock or 5xx keeps the upload (retry with an empty PATCH at
  `offset == length`), while 403/404/413 drop it. A committed row stays until it
  expires, so a client that lost the response learns from HEAD that the file
  landed, and a repeated final PATCH is idempotent. Staging lives under
  `<PP_BLOB_ROOT>/.uploads` for both backends; with the local backend the finished
  file is **renamed** into the store (`blob.Store.Ingest`) rather than copied.
- Web: a hand-written tus client whose chunks start at 4 MiB and follow measured
  throughput toward 15s per PATCH (clamped 256 KiB–64 MiB), halved after a
  failure and then sized from the rate the HEAD resync proves. Network errors,
  408/429/499/5xx and Cloudflare's 52x retry with backoff and a resync. The tray's
  **pause now stops transfers in flight**; the upload URL is memory-only, so a
  reload restarts the file and the abandoned upload expires.
- **Accounting.** `SumSpaceUsage` counts every stored version of every file, trash
  included, and the migration recomputed every space's `used_bytes` under that
  definition. `fs.EnsureRoom` replaces `checkQuota` and compares used plus
  incoming, so a new version costs its full size, and it checks **before the node
  is created** so a refused upload leaves no empty file. `version_retention_count`
  (default 100, 0 keeps everything) prunes beyond the newest N after each save and
  releases the blobs to GC; `GET /usage` gained `versions` and `trash` slices so
  the breakdown sums to the meter. Usage sums version sizes rather than distinct
  blobs, so a copy counts twice — the meter bounds what a space holds, not
  deduplicated disk.
- Deliberately out, still open under P1: per-user quota, file-count limits and
  egress accounting.
