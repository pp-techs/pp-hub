# M37 — Blob integrity

✅ done · part of the [delivery milestones index](../milestones.md).

- What made it urgent: a review of the local blob store found that GC could
  collect a blob in the moment between an upload deduplicating against it and
  the new version referencing it — the file deleted long ago, then uploaded
  again, came back pointing at nothing. Reproduced against Postgres before the
  fix; `TestCollectSparesABlobAnUploadJustDeduplicatedAgainst` holds it now.
- **Decision: the store claims before it installs.** `blob.Store`
  implementations take `blob.Claims` (`store.Queries.BlobClaims()`), and
  `ClaimBlob` inserts or re-pins the row (`pinned_until`, 6 h) before the store
  looks for an existing copy. GC deletes row and bytes in one transaction under
  the row lock, so a claim finds either a live copy or none. The claim also
  gives every refused write (quota, name conflict, crash) a row, which is what
  stopped it leaking bytes GC could not see.
- **Decision: `ref_count` belongs to the database.** Migration `0011` adds
  triggers on `node_versions`, `previews` and `users.avatar_blob` (cascades
  included) and recomputes every count; the Go `Incr`/`Decr` calls, the
  subtree hash listing and avatar `release` are gone. Previews are counted for
  the first time. `putFile` and a file copy are one transaction each.
- GC grace runs from `released_at` (when the count reached 0), not the row's
  `created_at`, and the sweep repeats "no version, preview or avatar names it"
  in SQL as a guard.
- `LocalStore` fsyncs a blob before it gets a name and the directory after the
  rename; replaces a same-named copy of the wrong length instead of
  deduplicating against it; and falls back to copy-then-rename when `.uploads`
  is on another filesystem (`EXDEV`). S3 dedups only against an object of the
  right length.
- `gc.Worker` gained a daily **audit** (remove stale temp files, recount,
  adopt bytes with no row — never delete) and an hourly **scrub**
  (`PP_BLOB_SCRUB_BYTES_PER_DAY`, default 100G, re-hashes blobs and marks
  `damaged_at`; the next write of that content heals it). New metrics:
  `pphub_blobs_damaged`, `pphub_blob_disk_free_bytes`,
  `pphub_blob_disk_size_bytes`.
- Tests: the conformance suite gained claim ordering, failed claims, heal and
  `Walk` for both backends (run against SeaweedFS too);
  `internal/gc/gc_db_test.go` covers the race, the refused-upload leak, the
  trigger counts through copy/prune/preview/avatar/purge, adoption and scrub.
  Details in [storage.md](../storage.md#garbage-collection).
