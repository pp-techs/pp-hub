# Internationalization

The SPA ships English and Vietnamese. Catalogs are gettext `.po` in the
repository, translated in a self-hosted Weblate, and compiled into the bundle
at build time. The Go server translates nothing.

## Why this shape

**Lingui, not i18next.** The app had ~900 strings already written inline in
JSX. Lingui derives a message id by hashing the source text, so migrating them
cost no key-naming decisions at all — `<Trans>New folder</Trans>` is the whole
edit. The ids never reach the catalog: `@lingui/format-po` writes the English
source as `msgid` and recomputes the hash on read, so a translator in Weblate
sees `New folder`, not `MbT6FE`.

**`.po`, not JSON.** Weblate treats gettext PO as a bilingual format with
first-class source/translation separation and `#:` source references, which are
the only context a translator gets. Its JSON formats report
`Supports plural: No` and would have to be configured as monolingual, with the
English text acting as a key.

**Weblate, not Tolgee/Crowdin.** Weblate is GPL-3.0-or-later with no seat cap
and no feature gates in the self-hosted build. Crowdin's free tier requires a
public repository; Tolgee's free self-hosted build caps at 10 seats and gates
SSO behind a licence key.

**No runtime catalog fetch.** `@lingui/vite-plugin` compiles every `.po` during
Vite's transform, so the bundle carries pre-compiled message trees and no ICU
parser. A new language is: translate in Weblate, merge the `.po`, add the tag to
`LOCALES`. There is deliberately no path for a deployer to drop a catalog into a
running container — with Weblate in place that case is served by a release, and
supporting it would cost a runtime ICU compiler plus a bind-mount onto the
nginx static root.

## Runtime

| Piece                                                  | File                                          |
| ------------------------------------------------------ | --------------------------------------------- |
| Locale list, detection, activation, `pageTitle`        | `apps/web/src/lib/i18n.ts`                    |
| `I18nProvider`, account reconciliation, `useSetLocale` | `apps/web/src/components/locale-provider.tsx` |
| Locale-bound date/size/sort helpers                    | `apps/web/src/lib/format.ts`                  |
| Catalogs                                               | `apps/web/src/locales/{en,vi}/messages.po`    |
| Extraction config                                      | `apps/web/lingui.config.ts`                   |

### Which locale wins

1. `users.settings.locale` — the account, once `GET /users/me` answers.
2. `localStorage["pp-hub-locale:v1"]` — this device's echo of that account
   preference, written every time one is applied.
3. `navigator.languages`.
4. `en`.

The `localStorage` step is what makes the first paint correct. The account is
the source of truth but arrives one round trip late, and `main.tsx` awaits the
catalog before the first render — so without a device-local echo, every
returning Vietnamese user would see a frame of English. `/login`,
`/s/{token}` and `/invite/{token}` have no account and live entirely on steps
2–4.

`users.settings` is a JSONB column that has existed since `0001_init.sql`.
`internal/users/preferences.go` gives it a typed _read_ view. Writes merge at
the JSON level and keep keys the binary has no field for, so a new preference
costs one Go field and one TypeScript field — never a migration, and never a
risk that an older code path erases a newer client's setting.

- Read: `GET /api/v1/users/me` returns `preferences`. It rides on the identity
  response because the language is needed before the first paint.
- Write: `PATCH /api/v1/users/me/preferences`, pointer fields, read-modify-write.
  A client that knows about one preference cannot blank the ones it has never
  heard of. It is deliberately not part of `PUT /users/me`, which is a full
  replace of `display_name` and `bio`.
- Every zero value means "never chosen". A `locale` defaulting to `"en"` would
  pin every existing account to English and make detection dead code.
- The server validates the tag's _shape_ only. An allowlist would make adding a
  language a backend release.

Theme and the default listing stay in `localStorage`/`ui-store`: they are facts
about a device, not a person. Language is the opposite, which is why it is the
one preference on the account.

### OnlyOffice

`POST /api/v1/edit-session?ui=<locale>`. The handler appends `&ui=` to the
Document Server URL (`internal/httpapi/wopi.go`), which reads it straight into
`editorConfig.lang`. `ui` is the resolved form of the WOPI discovery
placeholder `UI_LLCC` — `UI_LLCC` is not itself a parameter name. The client
sends its active locale rather than the server reading `users.settings`,
because that column is empty for anyone who never chose and the browser's
detection is then the only truthful answer.

## Writing translatable code

- **JSX text** → `<Trans>` from `@lingui/react/macro`.
- **Attributes, toasts, variables** → `const { t } = useLingui()` and the
  `` t`…` `` template tag. Never `t("…")`.
- **Module-scope constants** → `msg` descriptors from `@lingui/core/macro`,
  typed `MessageDescriptor`, resolved at render with `i18n._(descriptor)`. A
  module-level array is evaluated once at import time, before any catalog
  exists; rendered text there freezes the first language loaded and never
  follows a switch. This is the single most common way a string silently stops
  translating, and `lingui/t-call-in-function` is an error for that reason.
- **Route `head` titles** → `pageTitle(msg\`Trash\`)`. `head` runs outside
  React, so it uses the singleton. Titles follow the language on the next
  navigation rather than instantly.
- **Counts** → `<Plural>` / `plural()`. Never `` `${n} file${n === 1 ? "" : "s"}` ``.
  Vietnamese has only the `other` category; do not "fix" a `vi` plural by
  adding `one`.
- **A sentence is one message.** Splicing translated fragments assumes English
  word order.
- **Formatting** → `useFormatters()` from `@/lib/format`, which binds the
  active locale and re-renders on a switch. `lib/api/` takes the locale as an
  argument and never imports the i18n runtime; the dependency points one way.
- **`packages/ui` has no i18n dependency.** Its primitives read their
  screen-reader labels from `UiStringsProvider`
  (`packages/ui/src/lib/strings.tsx`), which the app fills in. A design-system
  package cannot know which i18n library its consumer chose.
- **Never translate**: the product name, file extensions, MIME types, HTTP
  methods, URL paths, cache keys, CSS classes, developer-facing `Error`
  messages, or language names in `LOCALES` (those are written in the language
  they name).

`eslint-plugin-lingui` runs as an Oxlint JS plugin — see the `lint` block in
the root `vite.config.ts`. `lingui/no-unlocalized-strings` warns on new
hardcoded text.

## Workflow

```bash
cd apps/web
bun run i18n:extract     # merge new messages into en + vi catalogs
bun run i18n:template    # refresh src/locales/messages.pot for Weblate
```

`--overwrite` is not optional on extract: without it the source catalog's
`msgstr` stays empty and Weblate reports English as 0% translated.

## Running Weblate

Weblate lives in `deploy/weblate/` and is deliberately **not** part of the
product stack. It is infrastructure for the people who translate pp-hub, not
for the people who run it: a self-hoster deploying the drive has no reason to
stand up a Django app, a second Postgres and a Valkey, and Weblate's own
documented minimum is 2 CPU / 3 GB RAM. Run it wherever the translation work
happens.

```bash
cp deploy/weblate/environment.example deploy/weblate/environment   # then edit
docker compose -f deploy/weblate/compose.yml up -d
docker compose -f deploy/weblate/compose.yml exec weblate cat /app/data/initial.pwd
```

It binds to `127.0.0.1:8090`. That is on purpose — it is an authenticated
admin surface holding write access to the repository, and it has no business
on a public interface without a TLS terminator in front of it.

Then give it the repository and create the component:

1. **Manage → SSH keys**, copy the key, and add it to the repository's
   **Deploy keys** with write access. GitHub accepts a given key on exactly
   one repository, so it cannot be one already used elsewhere.
2. Take an API token from `/accounts/profile/#api` and run:

```bash
export WEBLATE_URL=http://localhost:8090
export WEBLATE_TOKEN=wlu_...
export PP_REPO=git@github.com:pp-techs/pp-hub.git
./deploy/weblate/pp-weblate-setup.sh
```

The script is idempotent and creates the project and component over the REST
API. The configuration lives there rather than in a web form because it is the
part that is easy to get wrong and invisible once wrong — and because a form
does not survive rebuilding the instance.

### What the component is, and why

| Field                         | Value                                       |
| ----------------------------- | ------------------------------------------- |
| File format                   | `GNU gettext PO file` (`po`, **bilingual**) |
| File mask                     | `apps/web/src/locales/*/messages.po`        |
| Monolingual base              | _empty_                                     |
| Template for new translations | `apps/web/src/locales/messages.pot`         |
| Adding new translation        | `add` — create new language file            |
| Translation flags             | `icu-message-format`                        |
| `po_line_wrap`                | `65535` (`xgettext --no-wrap`)              |
| `po_no_location`              | `false` — keep the `#:` source references   |
| Push branch                   | `l10n/weblate`                              |
| Language filter               | `^(en\|vi)$`                                |

`po-mono` would be wrong: Lingui's output has English in `msgid`, which is the
bilingual shape. An empty `template` is what keeps it that way — a non-empty
one is how you get monolingual behaviour by accident.

`icu-message-format` is not optional. gettext components do not enable the ICU
check on their own, so without the flag a translator can break
`{count, plural, …}` and Weblate will not notice.

`po_no_location: false` overrides Weblate's default, which strips `#:` lines.
Those references are the only context a translator gets for a bare "Open" or
"Cancel". `po_line_wrap: 65535` matches Lingui's one-line-per-string output;
letting Weblate rewrap makes every round trip a whole-file diff.

Do **not** squash-merge the `l10n/weblate` branch — Weblate's docs are explicit
that squashing loses changes.

### Transport restrictions

Weblate 2026.x only fetches over schemes in `VCS_ALLOW_SCHEMES` — in practice
`ssh` and `https`. `git://` and local paths are refused with _"Fetching VCS
repository using … is not allowed"_, and it additionally blocks private and
internal addresses unless told otherwise. A self-hoster pointing it at an
internal Git host needs:

```
WEBLATE_VCS_ALLOW_HOSTS=git.internal.example
WEBLATE_VCS_RESTRICT_PRIVATE=0
```

The SSH deploy-key path above needs neither.

### Vietnamese plurals

Expect possible ICU selector warnings on `vi`: the check compares sub-message
selectors against the English source, which has `one`/`other` where Vietnamese
has only `other`. Add `icu-flags:-submessage_selectors` to the component's
translation flags if they appear. They did not on the current catalog — a full
scan of all 677 messages reported zero failing checks.

## Guardrails

`apps/web/tests/catalogs.test.ts` asserts that every translated message keeps
the placeholder set of its source and has balanced ICU braces, and that no
catalog carries a message the source does not define. Weblate runs its own ICU
check, but a catalog that arrived by any other route has had none.
